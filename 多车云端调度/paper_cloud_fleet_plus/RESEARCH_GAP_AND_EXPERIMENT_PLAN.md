# CloudFleet-OmniUQ 后续研究短板诊断与顶会级实验计划

## 1. 当前稿件距离顶会论文的主要差距

### 1.1 创新点不够“学术化”

当前 `paper_cloud_fleet/main.tex` 的主线更接近“工程系统整合”：

- 有地图、VDA5050、预约表、RL 调度、安全盾、监控前端。
- 但核心算法仍主要是“规则系统 + 轻量 RL 调度”的组合。
- 缺少一个足够强、足够清晰、可单独命名且可被同行复现的学术问题定义。

对一线论文来说，创新点至少要明确回答下面三件事中的两件：

1. 为什么现有方法在一个关键假设上失效。
2. 你的方法如何从建模层面修复这个失效。
3. 你的方法在更高难度、更大规模、更强扰动下仍成立。

当前稿件在第 1、2 点上都不够锋利。它现在的问题不是“不能讲”，而是“讲得太像系统说明书，不像研究论文”。

### 1.2 实验规模明显不够

当前稿件的占位实验有以下典型问题：

- 仅比较 3 个偏弱基线，缺少真正强基线。
- 缺少分层实验问题设计，例如“调度性能”“感知性能”“安全性能”“鲁棒性性能”“计算性能”分别验证。
- 没有大规模车队压力测试。
- 没有长时运行实验。
- 没有统计显著性设计。
- 没有真实感知闭环，只是调度层占位结果。

如果要对标顶会，至少要做到：

- 大规模仿真：`32 / 64 / 128 / 256` 台车，极限可到 `512`。
- 长时任务流：单次 `4h / 8h / 12h / 24h` 数字孪生运行。
- 多随机种子：每组 `5-10` 个 seeds。
- 异常注入：延迟、丢包、定位漂移、障碍穿行、局部感知缺失、边缘节点掉线。
- 多维指标：不仅吞吐，还要看死锁、近碰撞、调度延迟、能耗、UQ 校准误差、任务超时率。

### 1.3 缺少“感知-调度-控制”统一闭环

当前稿件的安全主要来自路网预约与规则约束，这对于静态或半静态车队足够，但不足以支撑高水平论文中的“复杂动态环境”叙事。

顶会级版本必须补上动态感知闭环：

- RGB 相机：识别人、叉车、托盘、临时障碍。
- 事件相机：处理高速穿越、频闪、逆光、低照度、动态模糊。
- LiDAR：提供稳定几何边界与占据。
- 多目标跟踪：把“检测框”转化为“可调度的动态占据风险”。
- 风险预测：把“当前观测”转化为“未来时间窗内的冲突概率”。

这样论文才能从“多车调度系统”升级为“感知增强、时延鲁棒、风险可校准的云边协同车队调度”。

### 1.4 缺少不确定性建模

当前稿件有安全盾，但没有真正的不确定性建模：

- 没有对通信时延进行状态外推。
- 没有对动态障碍未来运动分布建模。
- 没有对检测误差和跟踪误差建模。
- 没有风险校准指标。

如果加入 YOLO 和事件相机，却不加入 UQ，论文很容易退化为“多传感器堆料”，而不是研究创新。

建议把 UQ 放到方法主线中：

- 检测置信度校准。
- 轨迹预测方差估计。
- 预约风险 chance constraint。
- conformal calibration 或 temperature scaling。

### 1.5 缺少顶会级强基线

建议至少覆盖以下类别：

- 纯规则派单：Greedy / Nearest-job / Earliest-deadline-first。
- 经典 MAPF / MAPD：CBS、PIBT、TP/TPTS、Prioritized Planning。
- 纯预约系统：Reservation-only / traffic manager。
- RL/MARL：RTAW 类方法。
- 你当前稿件方法：CloudFleet-RS。
- 新方法：CloudFleet-OmniUQ。

如果篇幅不够，正文主对比保留 5 个，附录补全其余。

## 2. 建议升级后的论文主问题

建议把新论文的核心问题定义为：

> 在 VDA5050 约束下，如何在存在通信时延、动态障碍、异步感知和异构计算资源的条件下，完成大规模车队的安全调度与风险感知闭环优化？

这个定义比当前版本强很多，因为它同时绑定了：

- 工业协议约束。
- 动态环境挑战。
- 感知闭环。
- 时延问题。
- 大规模调度。
- 安全与吞吐双目标。

## 3. 建议的新方法主线

方法名建议：

- `CloudFleet-OmniUQ`
- 全称：`Perception-Aware Uncertainty-Calibrated Cloud-Edge Fleet Scheduling`

### 3.1 方法构成

1. **边缘多模态感知**
   - RGB 相机 + `YOLOv10`
   - 事件相机分支
   - 2D/3D LiDAR 占据建图
   - 多目标跟踪与速度估计

2. **动态风险预测**
   - 基于近几帧目标轨迹的 GRU / Transformer
   - 输出未来 `H` 步的占据概率图与意图分布

3. **云端分层调度**
   - 上层：任务分配
   - 中层：路权和时间窗分配
   - 下层：路径修正与等待策略

4. **不确定性感知安全盾**
   - 不是简单冲突检测
   - 而是 chance-constrained reservation
   - 约束形式：`P(collision) <= ε`

5. **异步时延补偿**
   - 对 state 时间戳进行外推
   - 对 VDA5050 状态延迟、乱序、丢包进行鲁棒处理

### 3.2 最值得打成论文贡献的三点

建议最后只把贡献收敛成 3 条：

1. 提出一个面向 VDA5050 的多模态感知增强型云边协同车队调度框架。
2. 提出一个不确定性感知的时空预约安全盾，将检测误差、通信时延和运动预测方差统一到 chance-constrained scheduling 中。
3. 构建顶会级数字孪生与实车实验协议，在大规模、多扰动、长时运行场景下验证吞吐、安全和鲁棒性优势。

## 4. 顶会级实验总设计

## 4.1 研究问题（RQ）

论文建议围绕 5 个 RQ 展开：

- `RQ1`：新方法在大规模车队下是否比强基线具有更高吞吐和更低死锁率？
- `RQ2`：加入 YOLO + 事件相机 + LiDAR 后，动态障碍场景下的任务完成率和近碰撞率是否显著改善？
- `RQ3`：不确定性建模是否真正降低了误判带来的过激调度或过度保守？
- `RQ4`：在通信延迟、丢包和感知失真条件下，新方法是否更稳健？
- `RQ5`：方法能否满足云端实时性与边缘部署成本约束？

## 4.2 场景矩阵

建议实验不是“一个仿真器跑全部”，而是按层设计：

### A. 数字孪生调度基准

- 地图 1：小型环形仓储
- 地图 2：中型多交叉口车间
- 地图 3：大型窄通道仓储
- 地图 4：园区配送混行场景

### B. 动态障碍感知基准

- 人员穿越
- 叉车横切
- 托盘临时占道
- 逆光 / 暗光
- 高频穿行和运动模糊

### C. 通信鲁棒性基准

- 固定延迟：`50 / 100 / 200 / 500 ms`
- 抖动延迟：`N(150, 50^2) ms`
- 丢包率：`0 / 1 / 3 / 5 / 10 %`
- 乱序比例：`0 / 2 / 5 %`

### D. 实车闭环基准

- `8-16` 台 AMR
- `2-4` 个动态行人/叉车干扰源
- 连续运行 `4-8h`
- 至少 `3` 天重复测试

## 4.3 车队规模与任务规模

参考一线工作，建议如下：

| 级别 | 车辆数 | 任务量/小时 | 运行时长 | 用途 |
|---|---:|---:|---:|---|
| 小规模 | 16 | 300-800 | 2h | 调参与可视化 |
| 中规模 | 32 / 64 | 800-2000 | 4h | 主体对比 |
| 大规模 | 128 / 256 | 2000-5000 | 8h | 可扩展性 |
| 极限压力 | 512 | 5000+ | 12-24h | 极限测试 |

正文主表展示到 `256` 即可，`512` 放附录更稳妥。

## 4.4 传感器配置建议

### 每台车边缘侧建议配置

- `2D LiDAR` 或 `3D LiDAR`
- 前向 `RGB` 相机
- 前向 `事件相机`
- IMU / 轮速计
- 工控机：Jetson Orin NX 或同级别

### 感知模型建议

- RGB 检测：`YOLOv10-S / YOLOv10-B`
- 事件分支：轻量 voxel / event-frame backbone
- 融合方式：late fusion 优先，便于先做稳健版本
- 跟踪器：ByteTrack / OC-SORT / EKF-IMM 自定义轨迹层

### 为什么要加事件相机

- 普通 RGB 在高速运动、频闪、背光、低照度时容易失效。
- 事件相机在微秒级时间分辨率下对动态边缘更敏感。
- 对车队调度最关键的不是“分类精细度”，而是“动态障碍出现得够不够早、轨迹预测稳不稳”。

因此事件相机不是为了做炫技感知，而是为了支撑“提前预约避让”的研究主线。

## 4.5 强基线配置

建议正文至少保留如下 6 个：

1. `Greedy+Reservation`
2. `Priority Planning`
3. `TP/TPTS`
4. `RTAW`
5. `CloudFleet-RS`
6. `CloudFleet-OmniUQ (ours)`

其中：

- `CloudFleet-RS` 是你当前版本，能证明新增模块不是“只换名字”。
- `RTAW` 代表学习型任务分配基线。
- `TP/TPTS` 代表经典 MAPD。
- `Greedy+Reservation` 和 `Priority Planning` 代表工程常用基线。

## 4.6 指标体系

### 调度性能

- 任务完成率
- 吞吐量（tasks/hour）
- 平均任务完成时间
- 平均等待时间
- 平均空驶距离
- SLA 超时率

### 安全性能

- 硬碰撞数
- 近碰撞数（小于安全距离阈值）
- 死锁恢复次数
- 紧急停车次数
- 风险盾回退比例

### 感知性能

- mAP50 / mAP50-95
- IDF1 / HOTA
- 轨迹预测 ADE / FDE
- 低照度场景召回率
- 高速横穿场景提前预警时间

### UQ 与校准

- ECE
- NLL
- Brier Score
- collision risk calibration gap

### 实时性

- 边缘感知延迟
- 边云通信延迟
- 云端调度延迟
- 端到端感知到决策延迟

## 7. 最重要的写作提醒

新论文最忌讳的事情不是“占位结果”，而是“占位结果却没有严谨实验协议”。

所以即使数据暂时未跑完，也要先把下面四件事写实：

- 场景矩阵
- 强基线集合
- 指标定义
- 日志与统计协议

只要这四件事是顶会级的，后续替换真实结果时整篇论文会很稳。

## 8. 参考一线工作的规模锚点

以下规模锚点可作为实验设计参照：

- `Wurman et al., 2008`：仓储中协调数百台协作机器人。
- `Ma et al., 2017`：MAPD 场景中强调在线任务流与数百 agent/task 的实时性。
- `Stern et al., 2019`：MAPF benchmark 统一术语与标准基准。
- `RTAW, 2022`：多机器人任务分配在仿真中扩展到 `1000` 台机器人。
- `DSEC, 2021`：事件相机大规模高动态范围数据集，含 `53` 条序列与同步 LiDAR。
- `YOLOv10, 2024`：高效实时检测主干，适合作为边缘视觉前端。
- `FlexEvent, 2024`：事件相机检测可扩展到 `20-180 Hz` 高频检测。

这些锚点说明：如果新论文仍停留在 `8-32` 台车、弱基线、无动态感知，那很难对标一线稿件。
